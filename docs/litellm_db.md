# Интеграция с базой данных LiteLLM

Auto AI Router может интегрироваться с базой данных PostgreSQL LiteLLM для логирования расходов и аутентификации API-ключей.

Атрибуция по командам на основе провайдера управляется серверным параметром `credential_name_as_team_id` и не зависит от настроек подключения к базе ниже.

## Конфигурация

```yaml
litellm_db:
  enabled: true
  is_required: false
  database_url: "os.environ/LITELLM_DATABASE_URL"
  max_conns: 25
  min_conns: 5
  log_queue_size: 5000
  include_team_spend_in_user_spend: true
```

## Параметры

| Параметр                           | Тип      | По умолчанию | Описание                                                              |
| ---------------------------------- | -------- | ------------ | --------------------------------------------------------------------- |
| `enabled`                          | bool     | false        | Включить интеграцию с БД LiteLLM                                      |
| `is_required`                      | bool     | false        | Останавливать запуск при ошибке подключения к БД                      |
| `database_url`                     | строка   | —            | Строка подключения PostgreSQL (поддерживает переменные окружения)     |
| `max_conns`                        | int      | 25           | Максимум подключений к базе                                           |
| `min_conns`                        | int      | 5            | Минимум подключений к базе                                            |
| `health_check_interval`            | длительность | 10s       | Интервал проверки здоровья БД                                         |
| `connect_timeout`                  | длительность | 5s        | Таймаут подключения                                                   |
| `auth_cache_ttl`                   | длительность | 20s       | TTL кэша аутентификации                                               |
| `auth_cache_size`                  | int      | 10000        | Размер кэша аутентификации                                            |
| `log_queue_size`                   | int      | 5000         | Размер очереди логов расходов                                         |
| `log_batch_size`                   | int      | 100          | Размер пакета логов расходов                                          |
| `log_flush_interval`               | длительность | 5s        | Интервал сброса логов расходов                                        |
| `include_team_spend_in_user_spend` | bool     | true         | Включать события команд в накопительную проекцию расхода пользователя |
| `log_retry_attempts`               | int      | 3            | Попытки повтора при ошибке вставки лога                               |
| `log_retry_delay`                  | длительность | 1s        | Задержка между попытками повтора                                      |
| `daily_spend_timezone`             | строка   | UTC          | Таймзона, по которой группируются daily-таблицы расходов              |

### Таймзона ежедневной агрегации

По умолчанию колонка `date` daily-таблиц расходов хранит **UTC**-календарный день запроса — тот день, по которому агрегирует сам LiteLLM. `daily_spend_timezone` сдвигает эту границу на локальный день: с `Europe/Moscow` запрос в `2026-03-10T22:30:00Z` учитывается в `2026-03-11`. Настройка влияет только на эту колонку — все таблицы, которые агрегирует AIR, берут день из одного вычисленного значения, поэтому не могут расходиться друг с другом, а хранимые временные метки (`LiteLLM_SpendLogs.startTime`, `created_at`/`updated_at`) остаются UTC.

## Возможности

- **Логирование расходов** — фиксирует использование токенов, стоимость и метаданные запросов
- **Ежедневная агрегация** — агрегирует расходы по пользователям, командам, организациям и end users
- **Аутентификация API-ключей** — проверяет API-ключи по verification токенам LiteLLM
- **Пакетная обработка** — логи группируются в пакеты и периодически сбрасываются для производительности
- **Dead Letter Queue** — неуспешные вставки логов сохраняются для повторной попытки

## Модели из базы данных LiteLLM {#models-from-the-litellm-database}

AIR загружает деплойменты из `LiteLLM_ProxyModelTable` и привязанных к ним креденшелов, поэтому флотом, управляемым через админ-панель LiteLLM, можно обслуживать без повторения в `config.yaml`. Сопоставление следует собственной семантике LiteLLM:

- **Привязка креденшелов** — деплоймент привязывается через `litellm_params.litellm_credential_name` (хранится зашифрованным мастер-ключом). Креденшл без собственного провайдера берёт его у деплойментов, которые его используют.
- **Провайдер** — `hosted_vllm` и `vllm` становятся типом `vllm`. Префикс `hosted_vllm/` в `litellm_params.model` удаляется до того, как запрос дойдёт до vLLM; остальные слэши (`Qwen/Qwen3-8B`) — часть идентификатора модели и сохраняются. Принимается и vLLM-деплоймент только с инлайновым `api_base` (без API-ключа).
- **Несколько деплойментов, одно имя** — деплойменты с общим `model_name` образуют один пул.
- **Алиасы** — `router_settings.model_group_alias` из `LiteLLM_Config` импортируется как публичные алиасы моделей. Как и в LiteLLM, алиас резолвится в целевую группу до выбора деплоймента, поэтому оба имени используют один набор деплойментов и общие лимиты скорости, состояние балансировщика и цену; алиас при этом остаётся в списке `/v1/models`. Ключ, в списке моделей которого есть любое из имён, может использовать алиас. Реальная группа моделей с именем алиаса имеет приоритет над алиасом, а `public_model_alias` из конфига — над импортированным.
- **Пропускается** — деплойменты с `blocked = true` и деплойменты с `mode: rerank` (`/rerank` не поддерживается).
- **Не импортируется** — `router_settings.fallbacks`. AIR осуществляет failover между креденшелами одной модели, а не между моделями, поэтому правила вида `coder-ultra -> qwen-ultra` игнорируются.
- **Параметры по умолчанию** — см. параметры по умолчанию vLLM.

## Идентификация пользователя

`user_header_mappings` LiteLLM заменён фиксированными заголовками. Заголовки `-Email` задают **end user** (`LiteLLM_EndUserTable`, `LiteLLM_DailyEndUserSpend`); заголовки `-Id` задают **пользователя**, записываемого в лог расходов и `LiteLLM_DailyUserSpend`. Заголовки `-Id` применяются только к сервисным ключам без владельца (`user_id` пустой); на ключе с владельцем они игнорируются и записывается владелец. Побеждает первый присутствующий заголовок (в этом порядке); пустые значения, длиннее 256 байт или непечатаемые игнорируются.

| Назначение | Заголовки, по убыванию приоритета                                              |
| ---------- | ------------------------------------------------------------------------------ |
| End user   | `X-AIR-User-Email`, `X-End-User`, `X-OpenWebUI-User-Email`, `X-AirClaw-User-Email` |
| User id    | `X-AIR-User-Id`, `X-OpenWebUI-User-Id`, `X-AirClaw-User-Id`                     |

Никакого фолбэка на тело запроса (`user`, `metadata.user_id`) нет, email владельца ключа никогда не используется как end user. Заголовки влияют только на статистику: аутентификация и проверки бюджета по-прежнему используют собственного пользователя ключа. Они принимаются на веру, поэтому сервисные ключи стоит выдавать только клиентам, которые выставляют их честно (обычно за OpenWebUI или другим шлюзом).

## Имена моделей в записях расходов

Как и в LiteLLM, `model` хранит имя модели провайдера, а `model_group` — имя, которое запросил клиент. Запрос алиаса `qwen-ultra`, обслуженный моделью `qwen397b-int4`, записывается как `model = qwen397b-int4`, `model_group = qwen-ultra`; оба ключа daily-таблиц заполняются соответственно. Для неуспешного запроса, не дошедшего до деплоймента, `model` откатывается к запрошенному имени.

## Строка подключения к базе

Строка подключения следует стандартному формату PostgreSQL:

```
postgresql://user:password@host:5432/litellm
```

Для безопасности используйте переменные окружения:

```yaml
litellm_db:
  database_url: "os.environ/LITELLM_DATABASE_URL"
```

```bash
export LITELLM_DATABASE_URL="postgresql://user:password@localhost:5432/litellm"
```
